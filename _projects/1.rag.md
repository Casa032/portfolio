A RAG application built locally.

# Process
 
AI is taking so much space in our lives right now, but with all the tools, agents and LLMs available, there's also the issue of data privacy. On top of that, an LLM knows nothing about our own documents. That's where RAG (Retrieval Augmented Generation) comes into play. As an example, it's like using ChatGPT with the files on our computer: we can query our own data and get answers based on it. Nonetheless, there's an issue: with ChatGPT, the model from OpenAI is still at play and our documents are sent to a remote server. That is solved with Ollama, which allows you to run your own models locally, given you have the required computational power (CPU/GPU).

Below, I present a project that allows me to have my own RAG (using AI models and documents) on my own computer.

All possible with Ollama and LangChain.

## Ollama 
Ollama is an open platform that gives users access to large language models, providing privacy, control and flexibility.

[ollama.com](https://ollama.com/)

After the download, you have access to a vast catalog of open-weight models. 

For this project, I'm using qwen3:4b-instruct-2507-q4_K_M, a small model (4 billion parameters, quantized in 4 bits) that runs on a regular laptop:
[qwen3:4b-instruct-2507-q4_K_M](https://ollama.com/library/qwen3:4b-instruct-2507-q4_K_M)

Just use this command in your terminal after installation to get the same model I used.

```bash
ollama pull qwen3:4b-instruct-2507-q4_K_M
```

## LangChain 

LangChain is an open-source framework for building applications and AI agents using large language models. 
[langchain.com](https://www.langchain.com/langchain)

The LangChain modules simplify our tasks: loading and parsing the documents, splitting them, connecting to the models and chaining everything together.

## Requirements

The Python libraries used in this project:

```bash
pip install langchain langchain-community langchain-ollama langchain-text-splitters langchain-chroma "unstructured[pdf]" ollama pandas streamlit
```

## The project 

Now, open your favorite IDE. Building the RAG application comes down to 5 steps.

### 1. Parsing the documents
First of all, we need to read the content of the documents that will constitute our knowledge base. All my PDFs go in a `data` folder. For this project, I'm using *Attention Is All You Need*, but any PDF added to the folder becomes part of the knowledge base.

```python 
import os
import logging
from langchain_community.document_loaders import UnstructuredPDFLoader

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

DATA_DIR = "data"

pdf_files = []
if os.path.exists(DATA_DIR):
    pdf_files = [f for f in os.listdir(DATA_DIR) if f.endswith(".pdf")]

if pdf_files:
    data = []
    for file in pdf_files:
        loader = UnstructuredPDFLoader(os.path.join(DATA_DIR, file))
        data.extend(loader.load())
    logger.info(f"Done loading {len(pdf_files)} file(s)")
else:
    logger.error("No PDF found, add at least one file in the data folder")
```

### 2. Splitting into chunks
After loading the files, we divide them into chunks. We need to split the documents into smaller parts to fit the context limits of the models and to get better embeddings (the transformation of text into vectors of numbers).

The size of the chunks matters a lot. Too small, they cut sentences in half. Too big, they mix several ideas. I tested three configurations (see the Evaluation part) and kept 500 characters with an overlap of 100, which gave the best results.

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=100)
chunks = text_splitter.split_documents(data)
```

### 3. Creating vector embeddings and storing them in a vector database
Those chunks will be embedded and stored in a vector database (Chroma).
For the embeddings, another model is necessary.
This one does the job: [nomic-embed-text](https://ollama.com/library/nomic-embed-text)

```python
import ollama 
ollama.pull('nomic-embed-text')
```

The database is saved on disk, so the embeddings are only computed once.

```python 
from langchain_ollama import OllamaEmbeddings
from langchain_chroma import Chroma

PERSIST_DIR = "chroma_db"

embeddings = OllamaEmbeddings(
    model='nomic-embed-text',
)

if os.path.exists(PERSIST_DIR):
    vector_db = Chroma(
        collection_name="simple_rag",
        embedding_function=embeddings,
        persist_directory=PERSIST_DIR,
    )
    logger.info("Vector database loaded from disk")
else:
    vector_db = Chroma.from_documents(
        documents=chunks,
        collection_name="simple_rag",
        embedding=embeddings,
        persist_directory=PERSIST_DIR,
    )
    logger.info("Vector database created and saved")
```

### 4. Retrieval
Then, the vector database is turned into a retriever. When the user asks a question, it is embedded with the same model, and a similarity search returns the chunks closest to it.

```python
retriever = vector_db.as_retriever()
```

### 5. Query and generation
Finally, the retrieved chunks are given to the LLM as context, along with the question of the user. The model answers based only on that context.

The retriever returns Document objects, so a small function keeps only their text before sending it to the prompt.

```python
from langchain_ollama import ChatOllama
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser

llm = ChatOllama(model='qwen3:4b-instruct-2507-q4_K_M')

template = """Answer the question based ONLY on the following context:
{context}
Question: {question}
""" 

prompt = ChatPromptTemplate.from_template(template)

def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)

res = chain.invoke("What is attention?")

print(res)
```

Output:

```text
Attention is a mechanism that maps a query and a set of key-value pairs to an output, enabling models to focus on relevant parts of input data. It is used in sequence modeling and transformation tasks, with self-attention being a common variant that relates different positions within a sequence. Attention mechanisms have become integral to modern neural networks and are applied in various tasks, including natural language processing and memory networks.
```

## Showing the sources

An answer is more trustworthy when we can check where it comes from. This function returns the answer and the chunks used to build it.

```python
def ask(question, retriever):
    docs = retriever.invoke(question)
    answer = (prompt | llm | StrOutputParser()).invoke(
        {"context": format_docs(docs), "question": question}
    )
    return answer, docs

answer, docs = ask("What is attention?", retriever)

print(answer)
for i, doc in enumerate(docs, 1):
    print(f"\nSource {i} ({doc.metadata.get('source', 'unknown')}):")
    print(doc.page_content[:200])
```

## Evaluation

To know if the RAG really works, I built a small test set: questions from the paper with the keywords the answer should contain. For each configuration of chunks, I check two things:
- **Retrieval hit**: are the keywords in the retrieved chunks?
- **Answer hit**: are the keywords in the final answer?

I also measure the response time. It's a simple metric (a keyword can be there without the answer being perfect), but it already shows the impact of the chunk size.

```python
import time
import pandas as pd

eval_set = [
    {"question": "What is attention?", "keywords": ["query", "key", "value"]},
    {"question": "How many heads are used in multi-head attention?", "keywords": ["8"]},
    {"question": "Which optimizer was used to train the Transformer?", "keywords": ["adam"]},
    {"question": "What BLEU score does the big Transformer reach on English-to-German translation?", "keywords": ["28.4"]},
    {"question": "What is the dimension of the model outputs (d_model)?", "keywords": ["512"]},
]

def evaluate(chunk_size, chunk_overlap):
    splitter = RecursiveCharacterTextSplitter(chunk_size=chunk_size, chunk_overlap=chunk_overlap)
    eval_chunks = splitter.split_documents(data)
    eval_db = Chroma.from_documents(
        documents=eval_chunks,
        collection_name=f"eval_{chunk_size}_{chunk_overlap}",
        embedding=embeddings,
    )
    eval_retriever = eval_db.as_retriever()

    results = []
    for item in eval_set:
        start = time.time()
        answer, docs = ask(item["question"], eval_retriever)
        elapsed = time.time() - start

        context = format_docs(docs).lower()
        results.append({
            "retrieval_hit": all(k in context for k in item["keywords"]),
            "answer_hit": all(k in answer.lower() for k in item["keywords"]),
            "time": elapsed,
        })

    df = pd.DataFrame(results)
    return {
        "chunk_size": chunk_size,
        "chunk_overlap": chunk_overlap,
        "retrieval_hit": df["retrieval_hit"].mean(),
        "answer_hit": df["answer_hit"].mean(),
        "avg_time_s": round(df["time"].mean(), 2),
    }

configs = [(100, 0), (500, 100), (1000, 200)]
summary = pd.DataFrame([evaluate(size, overlap) for size, overlap in configs])
print(summary)
```

Results:

| chunk_size | chunk_overlap | Retrieval hit | Answer hit | Avg time (s) |
|---|---|---|---|---|
| 100 | 0 | 60% | 60% | 11.46 |
| 500 | 100 | **100%** | **100%** | 31.77 |
| 1000 | 200 | 60% | 60% | 44.62 |

The middle configuration is the only one that answers all 5 questions correctly. With 100 characters, the chunks are too short: a number like the BLEU score can end up separated from the sentence that explains it, so the retriever misses it. With 1000 characters, each chunk mixes several ideas, its embedding becomes less precise, and the right passage is not always among the closest ones.

Retrieval hit and answer hit are identical in every configuration: when the right chunk is found, the model always uses it correctly. So the weak point of the RAG is the retrieval, not the LLM.

The response time grows with the chunk size, because the model has more context to read before answering. 500/100 is a good compromise between quality and speed.



## Performance

Everything runs on my laptop: [GPU]. With the chosen configuration, an answer takes about 32 seconds on average. It's slower than an online service, but nothing leaves my computer.

Like that, I have a RAG that runs only on my computer, without any external tools (information going who knows where).

## Limits and next steps

This version works, but there's still room for improvement: the test set has only 5 questions, so one question changes the score by 20%, and the evaluation is based on keywords, which is a simple metric. A 4B model also has its limits on complex questions. Next steps would be a bigger test set, a better evaluation (using an LLM as a judge, for example), adding a reranking step to improve the retrieval, which is the weak point here, and testing bigger models on a GPU to keep a reasonable response time.
